## 2. Аналіз початкового проєкту

Для роботи було використано готовий застосунок **Orders API**, розроблений на Node.js та Express.

Програма дозволяє створювати, отримувати та видаляти замовлення через HTTP-запити.

Під час аналізу початкового файлу `app.js` було виявлено декілька проблем.

**Проблема №1. Змішування відповідальностей**

В одному файлі знаходилися налаштування сервера, маршрути, перевірка даних, обчислення вартості замовлень і робота зі сховищем.

Це ускладнювало читання коду, пошук помилок і подальший розвиток програми.

**Проблема №2. Непотрібна функція `slopify()`**

Функція лише виводила повідомлення в консоль і передавала запит наступному обробнику.

**Проблема №3. Штучні затримки**

У програмі використовувалася функція `synchronizeOrderState()`, яка створювала затримку приблизно 900–2000 мс.

Це значно сповільнювало створення та отримання замовлень.

## 3. Рефакторинг структури проєкту

Під час виконання роботи було створено три додаткові модулі.

### `app.js` — головний файл

Залишено тільки основні налаштування сервера:

- створення застосунку Express;
- налаштування обробки JSON;
- підключення маршрутів;
- обробку помилок;
- запуск HTTP-сервера.

Таким чином, головний файл став значно коротшим і зрозумілішим.

### `routes/orders.js` — маршрути API

У цей модуль перенесено обробку HTTP-запитів:

| Метод | Маршрут | Призначення |
|---|---|---|
| GET | `/health` | Перевірка роботи сервера (у `app.js`) |
| GET | `/orders` | Отримання всіх замовлень |
| GET | `/orders/:id` | Отримання замовлення за ID |
| POST | `/orders` | Створення замовлення |
| DELETE | `/orders/:id` | Видалення замовлення |

Тепер маршрути відповідають за отримання запитів і формування HTTP-відповідей, а бізнес-логіка виконується окремо.

### `service/orders.js` — бізнес-логіка

Цей модуль відповідає за:

- перевірку правильності введених даних;
- створення замовлень;
- розрахунок загальної вартості;
- підготовку даних для відповіді;
- взаємодію зі сховищем.

Наприклад, під час створення замовлення програма перевіряє наявність імені клієнта, списку товарів, їхньої кількості та ціни.

### `store/orders.js` — зберігання даних

У цьому модулі реалізовано роботу із замовленнями в оперативній пам'яті.

Основні функції:

- `add()` — додавання замовлення;
- `list()` — отримання списку;
- `findById()` — пошук за ідентифікатором;
- `removeById()` — видалення замовлення.

Такий підхід дозволяє відокремити роботу з даними від HTTP-маршрутів.

### Підсумкова архітектура

`app.js` → `routes/orders.js` → `service/orders.js` → `store/orders.js`

Кожен модуль тепер відповідає за конкретну частину функціональності.

## 4. Очищення та оптимізація коду

### Зміна №1. Видалення `slopify()`

У початковому коді знаходилася функція:

```javascript
function slopify(req, res, next) {
  console.log("iam lazy and i dont know what my code does");
  next();
}

app.use(slopify);
```

Функція не виконувала корисної бізнес-логіки, а лише створювала зайві повідомлення в консолі.

**Рішення:** функцію та її підключення було видалено.

Це зробило виконання запитів чистішим і прибрало непотрібне логування.

### Зміна №2. Усунення штучного очікування

У початковому коді використовувалася функція `synchronizeOrderState()`, яка створювала випадкові затримки.

Оскільки замовлення зберігаються у звичайному масиві в оперативній пам'яті, реальної синхронізації з віддаленою системою не відбувалося.

**Рішення:** усунуто необґрунтоване очікування, а операції над даними виконуються безпосередньо.

Саме це стало основною причиною покращення швидкодії.

### Зміна №3. Розділення HTTP-логіки та бізнес-логіки

Раніше обробка запитів і операції із замовленнями знаходилися разом.

Після рефакторингу маршрут отримання замовлення має зрозумілу структуру:

```javascript
router.get("/:id", (req, res) => {
  const order = service.getOrder(req.params.id);

  if (!order) {
    return res.status(404).json(
      service.notFoundProblem()
    );
  }

  return res.status(200).json(
    service.orderResponse(order)
  );
});
```

Тепер маршрут лише отримує ID, викликає відповідну функцію сервісу та повертає результат.

Це спрощує підтримку й тестування.

### Зміна №4. Збереження API-контракту

Під час рефакторингу було збережено основні маршрути, правила валідації, розрахунок `total` та формати HTTP-відповідей.

Це важливо, оскільки рефакторинг має покращувати внутрішню реалізацію програми без порушення її зовнішньої поведінки.
